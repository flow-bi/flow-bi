# FRONTEND.md

## 1. 문서 목적과 범위

- 범위: 프런트엔드 아키텍처와 구현 기준

이 문서는 화면 구현보다 구조와 데이터 흐름을 정의한다. 기능 요구사항과 업무 규칙은 승인된 Product Spec, UI 기준은 DESIGN.md를 따른다.

## 2. 기술 스택

| 구분                 | 기술               |
| -------------------- | ------------------ |
| UI                   | React + TypeScript |
| Build                | Vite               |
| 서버 상태            | TanStack Query     |
| 클라이언트 전역 상태 | Zustand            |
| Form                 | React Hook Form    |
| Schema 검증          | Zod                |
| Styling              | Tailwind CSS       |
| Package Manager      | npm                |

미확정 기술은 기능 구현의 필요만으로 임의 선택하지 않는다. Design Doc 또는 Active Plan에서 근거와 검증 방법을 정하고 승인을 받은 뒤 도입한다.

## 3. 책임과 경계

프런트엔드는 다음을 담당한다.

- 인증된 사용자에게 화면을 제공한다.
- 승인된 Product Spec의 기능 요구사항을 화면과 상호작용으로 구현한다.
- 사용자의 입력과 API 응답의 화면 상태를 표현한다.
- 반응형 레이아웃과 접근성 경험을 관리한다.

프런트엔드는 다음의 최종 책임자가 아니다.

- 인증·권한 판정
- 비즈니스 규칙과 데이터 정합성
- 서버 검증과 데이터 공개 범위의 최종 판정

## 4. 기본 소스 구조

```text
frontend/
├── src/
│   ├── app/          # 앱 초기화, Provider, Router, 전역 설정
│   ├── pages/        # 라우트 단위 화면 조립
│   ├── features/     # 기능별 UI, 상태, API 연결
│   ├── entities/     # 안정된 핵심 도메인 표현
│   ├── shared/       # 범용 UI, 유틸리티, API 기반 코드
│   └── assets/       # 정적 자산
└── tests/            # 공통 테스트 설정이 필요한 경우
```

- 기능 코드는 features/{feature-name}/ 안에서 응집한다.
- 기능 경계는 화면 이름이 아니라 승인된 Product Spec과 도메인 책임을 기준으로 정한다.
- pages는 라우트 조립을 담당한다.
- shared는 특정 도메인 의미를 가지지 않는다.
- 기능 간 내부 파일을 직접 참조하지 않고 공개 진입점을 통해 의존한다.
- 초기에는 사용하지 않는 계층과 빈 디렉터리를 만들지 않는다.
- 순환 의존을 허용하지 않는다.

## 5. 상태 관리

- 서버 데이터는 TanStack Query가 소유한다.
- 여러 화면에서 공유되는 클라이언트 상태는 Zustand로 관리한다.
- 한 컴포넌트나 가까운 트리에서만 사용하는 UI 상태는 로컬 상태로 유지한다.
- 폼 상태는 React Hook Form, 검증은 Zod를 사용한다.
- 같은 서버 데이터를 여러 저장소에 중복 관리하지 않는다.
- 조회 조건이 공유·북마크·뒤로 가기 대상이면 URL 상태로 표현한다.
- Query Key에는 사용자·권한·조회 범위를 반영하고, 로그아웃 또는 인증 사용자 변경 시 사용자별 캐시를 제거한다.
- Mutation 성공 후 영향받는 Query만 갱신하거나 무효화한다.
- 낙관적 갱신은 실패 시 복구와 충돌 처리가 명확하고 테스트되는 경우에만 사용한다.

## 6. API와 오류 처리

- API 요청·응답 타입과 URL은 기능별 API 경계에 둔다.
- UI 컴포넌트는 원시 HTTP 세부사항에 직접 의존하지 않는다.
- 응답 DTO를 화면 모델로 변환할 수 있지만 원래 계약의 의미를 바꾸지 않는다.
- Mock과 임시 타입은 실제 API 계약과 일치해야 하며 임시 상태를 완료 결과에 남긴다.
- 네트워크·서버 오류는 공통 오류 모델로 변환하고, 적절한 화면 상태로 표시한다.
- 오래된 요청이 최신 화면 상태를 덮어쓰지 않도록 한다.
- 오류가 발생해도 기존의 유효한 데이터를 무조건 제거하지 않으며 재시도 가능한 오류에는 재시도 수단을 제공한다.

## 7. 테스트와 성능

- 순수 함수/Schema, 컴포넌트 동작, API 경계를 통제한 화면 통합과 핵심 사용자 흐름을 검증한다.
- 테스트는 구현 세부보다 사용자가 관찰 가능한 동작을 중심으로 한다.
- 대량 데이터 화면은 필요한 범위만 조회하고, 필요 시 페이지네이션·가상화·검색 제한을 검토한다.
- 성능 최적화와 지연 로딩은 측정 결과와 사용자 영향을 근거로 적용한다.

## 8. 결정 기준

- 구조 변경, 상태 저장소 추가, 패키지 도입은 Design Doc/ADR/Active Plan에서 근거를 남기고 승인한다.
- 기능별 UI·UX 세부 규칙은 DESIGN.md를, 실행 규칙은 AGENTS.md를 따른다.
