# 커밋 메시지 작성 스킬 (commit-helper)

이 스킬은 프로젝트의 깃모지 및 이슈 번호 기반 커밋 컨벤션에 맞춰 커밋 메시지를 작성하고 사용자 승인을 거쳐 커밋을 진행합니다.

## 📌 커밋 메시지 작성 절차 (Steps)

1. **`git diff` 및 `git status` 검토**: 현재 스테이징/비스테이징 상태의 모든 변경사항을 확인합니다.
		- 신규 파일은 `git diff`에 표시되지 않을 수 있으므로 파일 내용을 별도로 확인합니다.
2. **변경사항 논리적 분리 판단**: 
   * 변경 파일이 여러 개이거나 서로 다른 성격(예: `feat`, `fix`, `docs`, `refactor`)의 작업이 섞여 있는 경우, 커밋을 2개 이상으로 분할할지 판단합니다.
3. **분할 커밋 메시지 제안**:
   * **[단일 커밋]** 변경사항이 단일 성격일 경우: 1개의 커밋 메시지 제안
   * **[분할 커밋]** 작업 성격이 다를 경우: 파일/도메인 단위별로 나누어 각 커밋 순서와 스테이징 명령어(`git add <파일>`), 커밋 메시지 초안을 함께 제안합니다.
4. **사용자 확인 후 순차 커밋 수행**: 사용자 승인 시 제안된 순서에 맞춰 `git add`와 `git commit`을 순차적으로 수행합니다.
	- 사용자 승인 전에는 `git add`, `git commit`, `git push`를 실행하지 않습니다.
	- 커밋 승인에는 원격 저장소 Push 승인이 포함되지 않습니다.
	- `git push`는 별도의 명시적 요청이 있을 때만 수행합니다.

## 📐 프로젝트 커밋 규칙 (Commit Rules)

### 1. 작성 형식

<깃모지> / #<이슈번호> - <커밋 메시지>

* **예시**: `✨ / #18938 - 사용자 로그인 API 및 DTO 추가`
* **예시**: `🐛 / #12 - JWT 토큰 만료 예외 처리 수정`

### 1-1. 이슈 번호 확인 순서

1. 현재 브랜치명에서 이슈 번호를 확인합니다.
2. Active Plan 또는 관련 작업 문서에서 이슈 번호를 확인합니다.
3. 최근 대화나 사용자가 제공한 번호를 확인합니다.
4. 확인할 수 없다면 임의로 생성하지 않고 사용자에게 이슈 번호를 요청합니다.

### 2. 커밋 메시지 작성 구조

- 제목은 변경 결과를 중심으로 간결하게 작성합니다.
- 변경 이유가 메시지 이해에 중요한 경우에만 Why와 What을 함께 작성합니다.
- 상세한 배경이나 구현 설명이 필요한 경우 커밋 본문에 작성합니다.

### 3. 문체 및 기본 규칙
* **언어**: 한국어로 작성합니다.
* **시제**: 현재형 명사/동사형으로 요약합니다.
* **이슈 연동**: 관련된 이슈 번호가 확인되면 `#이슈번호`를 필수 기재합니다.

### 4. 커밋 분할 규칙
* **관심사 분리**: 기능 추가(`feat`), 버그 수정(`fix`), 문서 수정(`docs`) 등 깃모지 타입이 서로 다른 파일들은 절대로 하나의 커밋으로 묶지 않고 분리 커밋을 제안합니다.
* **부분 스테이징**: 분할 커밋 시 사용자에게 파일별 `git add <filepath>` 명령어를 명확히 안내한 뒤 개별 커밋합니다.

| **리팩토링** | ♻️ | `:recycle:` | `refactor` |
| **설정 / 환경 작업** | 🔧 | `:wrench:` | `chore` |
| **문서 작업** | 📝 | `:memo:` | `docs` |
| **테스트** | ✅ | `:white_check_mark:` | `test` |
| **CI 설정** | 👷 | `:construction_worker:` | `ci` |
| **배포** | 🚀 | `:rocket:` | `deploy` |
