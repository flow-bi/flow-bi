# ADR-001: Redis를 사용하는 서버 세션 인증 채택

[ADR 인덱스로 돌아가기](../ADR.md)

## 메타데이터

- 상태: Accepted
- 결정일: 2026-08-07
- 저장소 반영일: 2026-08-09
- 결정 대상: 브라우저 사용자 인증과 로그인 상태 관리
- 대체하는 결정: JWT Access Token + Refresh Token 기반 브라우저 인증
- 대체된 ADR: 없음

## Context

flow-bi는 관리자가 발급한 사번과 임시 비밀번호로 로그인하는 브라우저 기반 그룹웨어다. 한 사용자는 여러 브라우저나 기기에서 동시에 로그인할 수 있어야 하며 서버는 다음 보안 이벤트에 맞춰 사용자별 로그인 상태를 즉시 통제해야 한다.

- 사용자가 비밀번호를 변경하면 현재 세션은 유지하고 다른 세션은 모두 종료한다.
- 관리자가 비밀번호를 초기화하면 대상 사용자의 모든 세션을 종료한다.
- 역할 또는 주요 권한이 변경되면 이전 권한을 가진 모든 세션을 종료한다.
- 여러 Backend 인스턴스가 동일한 로그인 상태를 공유해야 한다.

JWT를 완전한 Stateless 방식으로 사용하면 만료되지 않은 Access Token을 즉시 또는 선택적으로 폐기하기 어렵다. 이를 보완하려면 Refresh Token 저장소, 회전, 폐기, Blacklist 또는 Token Version과 같은 별도 상태 관리가 필요하다. 현재 요구사항에서는 Stateless 인증의 이점보다 서버가 인증 상태를 직접 통제하는 능력이 더 중요하다.

## Decision

브라우저 인증은 JWT 대신 Spring Security, HttpSession과 Spring Session Redis를 사용하는 서버 세션 방식으로 구현한다.

### 인증과 저장 경계

- 사용자는 사번과 비밀번호로 로그인한다.
- 인증 이후 Principal 이름은 변경 가능한 사번이 아니라 불변 내부 `userId`의 문자열 표현을 사용한다.
- Spring Session의 indexed Redis repository를 공용 Session Store로 사용한다.
- 브라우저에는 사용자 정보를 포함하지 않는 불투명한 Session Cookie만 전달한다.
- Session Cookie에는 `HttpOnly`, `Secure`, `SameSite` 정책을 적용한다.
- PostgreSQL에는 브라우저 Refresh Token을 저장하지 않으며 `user_tokens` 테이블을 두지 않는다.
- `user_credentials.must_change_password`가 임시 비밀번호 변경 필요 상태의 영속 기준이다.

### Principal 인덱스와 세션 형식

- Principal 인덱스는 `FindByIndexNameSessionRepository.PRINCIPAL_NAME_INDEX_NAME`과 내부 `userId`를 사용한다.
- 사용자별 물리 세션 조회와 정리는 `findByPrincipalName(userId)`와 `deleteById(sessionId)`를 사용한다.
- 세션에는 Spring Security Context, 생성·최근 접근·만료 정보와 로그인 시점의 `AUTH_GENERATION`만 포함한다.
- 비밀번호, 비밀번호 해시, 임시 비밀번호, 사번과 변경 가능한 일반 프로필 정보는 세션에 저장하지 않는다.
- 애플리케이션은 Spring Session이 소유하는 Redis 내부 Key와 직렬화 형식을 직접 조작하지 않는다.

### 원자적 무효화

- 사용자별 세션 세대는 `flow-bi:auth:session-generation:{userId}`에 저장한다.
- 비밀번호 또는 권한 변경의 진행 상태는 `flow-bi:auth:session-change:{userId}`에 저장한다.
- 보안 이벤트 시작 시 하나의 Redis 원자 연산으로 세대를 증가시키고 변경 진행 상태를 기록한다.
- 변경 진행 중에는 새 로그인을 거부한다.
- 모든 인증 요청은 세션의 `AUTH_GENERATION`과 현재 세대를 비교하며, 세대가 다르면 즉시 거부한다.
- 사용자 본인의 비밀번호 변경에 한해 변경 진행 상태에 기록된 현재 session ID를 유지한다. DB 변경 후 현재 세션을 새 세대로 갱신하고 나머지 세션을 삭제한다.
- 관리자 비밀번호 초기화와 역할·주요 권한 변경에는 유지 세션을 두지 않는다.
- 세대 증가가 논리적 무효화의 기준이며 Principal 인덱스를 통한 세션 삭제는 멱등 물리 정리다.
- Redis 상태 조회나 원자 연산이 실패하면 인증과 보안 변경을 기본 거부한다.

## Consequences

### Positive

- 로그아웃과 보안 이벤트에 맞춰 기존 로그인 상태를 즉시 통제할 수 있다.
- 비밀번호 변경 시 현재 세션만 선택적으로 유지할 수 있다.
- 여러 Backend 인스턴스가 같은 인증 상태를 공유하므로 애플리케이션 서버를 수평 확장할 수 있다.
- 프런트엔드에서 Access Token과 Refresh Token을 저장·갱신하는 책임이 사라진다.
- 역할 강등 후 기존 세션에 이전 권한이 남는 문제를 차단할 수 있다.
- 물리 세션 삭제가 부분 실패해도 세대 비교를 통해 기존 세션을 논리적으로 거부할 수 있다.

### Negative

- 인증 요청이 Redis 가용성과 네트워크 I/O에 의존한다.
- 시스템 전체는 인증 상태를 Redis에 저장하는 Stateful 구조가 된다.
- 사용자별 세대와 변경 진행 상태를 모든 인증 요청에서 검증해야 한다.
- Redis 장애, 세대 Key 유실과 변경 진행 중 실패에 대한 복구 및 관측 정책이 필요하다.
- 외부 API, 모바일 또는 서비스 간 인증이 필요해지면 별도 Token 기반 인증 전략이 필요할 수 있다.

## Alternatives Considered

### JWT Access Token + Refresh Token

Access Token을 독립적으로 검증할 수 있지만 만료 전 즉시 폐기와 현재 기기만 유지하는 정책을 구현하려면 별도의 Token 상태 저장과 수명주기 관리가 필요하므로 채택하지 않았다.

### 애플리케이션 서버 메모리 Session

구현은 단순하지만 세션이 특정 서버에 종속되고 서버 장애와 수평 확장에 불리하므로 채택하지 않았다.

### Principal 인덱스 조회 후 세션 순회 삭제만 사용

구현은 단순하지만 동시 로그인과 Redis 부분 실패 시 삭제되지 않은 세션이 계속 유효할 수 있다. 따라서 세대 기반 논리 무효화를 우선 적용하고 순회 삭제는 후처리로 사용한다.

## 구현 제약

- Spring Session은 Principal 조회가 가능한 indexed Redis repository로 구성한다.
- Spring Session 내부 Redis Key를 애플리케이션 코드에서 직접 삭제하지 않는다.
- 세대 Key가 유실됐는데 활성 세션이 존재하거나 변경 진행 상태가 남아 있으면 복구 전까지 인증을 실패 폐쇄한다.
- 세대 및 변경 진행 Key의 TTL은 모든 사용자 세션과 최대 복구 시간보다 길어야 한다.
- 실제 DB Migration에서는 기존 계정의 `must_change_password` 초기값과 배포 전환 절차를 검증한다.
- 로그인, 비밀번호 변경, 관리자 초기화, 역할 변경, 세션 무효화 실패를 감사 가능하게 기록한다.

## 미확정 사항

- 세션 유휴 만료 시간과 절대 만료 시간
- Session Cookie 이름과 `SameSite`의 구체 값
- CSRF Token 전달과 검증 방식
- Redis 운영 가용성, Keyspace Event와 장애 복구 구성
- 기존 계정의 `must_change_password` Migration 초기값
