# 인증 및 권한 Design Doc

이 문서는 인증, 세션, 권한 판단처럼 여러 기능에서 공통으로 참조하는 기술 설계 결정을 관리한다. 로그인 화면의 기능 요구사항은 `docs/product-specs/auth.md`, 관리자 기능 요구사항은 `docs/product-specs/admin.md`를 기준으로 한다.

## 적용 범위

- 로그인 이후 서비스 접근 전제
- 사용자 기본 정보와 인증 정보의 책임 분리
- Redis 기반 로그인 세션 관리 방향
- 최초 로그인 및 비밀번호 변경 정책
- 관리자 기능 접근을 포함한 역할 기반 권한 판단
- 시스템 관리자와 인사팀 관리자의 권한 범위

## 설계 결정

### 1. 인증된 사용자 맥락을 서비스 접근의 기본 전제로 둔다

#### 결정

그룹웨어의 주요 기능은 로그인한 사용자를 기준으로 동작한다. 사용자별 일정, 헤더 표시 이름, 마이페이지, 관리자 접근, 알림 정책은 인증된 사용자 맥락을 기준으로 판단한다.

#### 근거

- `requirements.md` NFR-001은 로그인 사용자만 서비스 이용 가능해야 한다고 정의한다.
- `core-beliefs.md`는 서비스 기능을 로그인한 사용자 기준으로 판단한다고 정의한다.
- `backend/DB_SCHEMA.md`의 일정 등록자, 사용자 역할, 인증 정보, 소속 팀 정보는 사용자와 연결되어 있다.

#### 영향

개별 기능은 익명 사용자 흐름을 기본 전제로 두지 않는다. 인증이 필요한 화면과 데이터 조회는 사용자 식별 정보를 기준으로 접근 범위를 판단한다.

### 2. 사용자 기본 정보와 인증 정보는 분리한다

#### 결정

임직원 기본 정보와 비밀번호 해시, 세션 같은 인증 정보는 같은 책임으로 다루지 않는다. 사용자 기본 정보는 조직도, 마이페이지, 관리 기능에서 사용하고, 인증 정보는 로그인과 세션 유지에 한정해 다룬다.

#### 근거

- `backend/DB_SCHEMA.md`는 `users`를 임직원 핵심 정보 관리 테이블로 정의한다.
- `backend/DB_SCHEMA.md`는 `user_credentials`를 비밀번호 해시 값을 인사 정보와 격리하기 위한 테이블로 설명한다.
- `requirements.md` NFR-002는 비밀번호를 암호화하여 저장해야 한다고 정의한다.
- `core-beliefs.md`는 민감 정보와 권한 판단을 일반 정보와 분리한다고 정의한다.

#### 영향

조직도, 직원 목록, 마이페이지 같은 사용자 정보 조회 기능은 인증 민감 정보를 함께 노출하지 않는다. 인증 기능 변경 시에도 사용자 기본 정보 기능의 책임과 분리해 검토한다.

### 3. 로그인 계정은 사용자와 1:1로 연결한다

#### 결정

한 명의 임직원은 시스템 내에서 하나의 고유한 인증 정보 세트를 가진다.

#### 근거

- `backend/DB_SCHEMA.md`는 `users`와 `user_credentials`의 관계를 1:1로 설명한다.
- `backend/DB_SCHEMA.md`는 `user_credentials.user_id`에 Unique 제약조건을 두어 한 사용자에게 하나의 인증 정보 세트만 연결되도록 설명한다.

#### 영향

인증 정보는 사용자 단위로 식별된다. 하나의 임직원에게 여러 자체 로그인 계정을 부여하는 흐름은 현재 확정된 설계 범위에 포함하지 않는다.

### 4. 로그인 세션은 여러 기기 사용을 고려해 관리한다

#### 결정

브라우저 인증은 JWT가 아니라 Redis를 공용 Session Store로 사용하는 서버 세션 방식을 사용한다.

한 사용자는 여러 기기나 브라우저에서 동시에 로그인할 수 있고, 내부 `userId`를 Principal로 사용해 사용자별 세션을 조회하고 무효화할 수 있어야 한다.

#### 근거

- Redis를 공용 Session Store로 사용하면 여러 백엔드 인스턴스가 로그인 상태를 공유하면서 사용자별 세션을 중앙에서 통제할 수 있다.
- 브라우저가 HttpOnly Cookie를 관리하므로 프런트엔드의 Access Token·Refresh Token 저장 및 갱신 책임을 제거할 수 있다.

#### 영향

Spring Security가 인증을 생성하고 Spring Session이 HttpSession을 Redis에 저장한다. 브라우저에는 `HttpOnly`, `Secure`, `SameSite`가 적용된 Cookie로 불투명한 세션 식별자만 전달한다.

세션에는 내부 `userId`, Authentication/SecurityContext, 역할 또는 권한, 생성·최근 접근·만료 정보 등 인증 유지에 필요한 최소 정보만 둔다. 비밀번호, 비밀번호 해시, 임시 비밀번호와 변경 가능한 일반 사용자 정보는 저장하지 않는다.

로그아웃은 현재 세션을 무효화한다. 사용자 비밀번호 변경은 현재 세션을 유지하고 다른 세션을 무효화하며, 관리자 비밀번호 초기화와 역할·주요 권한 변경은 대상 사용자의 모든 세션을 무효화한다. 구체적인 기기 관리 화면과 모든 기기 로그아웃 UI는 현재 Product Spec 범위에 포함하지 않는다.

#### Principal 인덱스 계약

- Spring Session은 Principal 조회가 가능한 indexed Redis repository를 사용한다.
- Principal 이름은 변경될 수 있는 사번이 아니라 내부 `userId`의 문자열 표현으로 고정한다.
- 로그인 성공 시 `FindByIndexNameSessionRepository.PRINCIPAL_NAME_INDEX_NAME`이 같은 Principal 값으로 채워졌는지 검증한다.
- 사용자별 물리 세션 조회는 `findByPrincipalName(userId)`를 사용하고, 삭제는 Session Repository의 `deleteById(sessionId)`를 사용한다.
- 애플리케이션은 Spring Session이 소유하는 Redis 내부 Key를 직접 조작하지 않는다.

#### 세션 저장 형식

- Spring Session이 session ID, 생성 시각, 최근 접근 시각, 최대 비활성 시간과 만료 정보를 관리한다.
- `SPRING_SECURITY_CONTEXT`에는 내부 `userId`를 이름으로 갖는 Principal과 현재 역할·권한을 저장한다.
- 애플리케이션 세션 속성 `AUTH_GENERATION`에는 로그인 시점의 사용자별 세션 세대를 정수로 저장한다.
- 비밀번호, 비밀번호 해시, 임시 비밀번호, 사번과 변경 가능한 일반 프로필 정보는 세션에 저장하지 않는다.
- Spring Session 내부 저장 구조와 직렬화는 Repository 소유의 불투명한 형식으로 취급하고 공개 계약이나 도메인 코드가 의존하지 않는다.

#### 원자적 세션 무효화 계약

- 사용자별 Redis 상태는 `flow-bi:auth:session-generation:{userId}`와 `flow-bi:auth:session-change:{userId}`로 분리한다. 두 Key에는 개인정보나 권한 정보를 저장하지 않는다.
- 로그인은 변경 진행 Key가 없을 때만 현재 세대를 읽어 새 세션의 `AUTH_GENERATION`에 기록한다. 기존 세션이 있는 상태에서 세대 Key가 유실되면 값을 임의 초기화하지 않고 인증을 실패 처리한다.
- 모든 인증 요청은 세션의 `AUTH_GENERATION`과 현재 사용자 세대를 비교한다. 세대가 다르거나 변경 진행 상태이면, 변경 진행 Key에 유지 대상으로 기록된 현재 session ID를 제외하고 즉시 인증 실패로 처리한다.
- 사용자 본인 비밀번호 변경은 하나의 Redis 원자 연산으로 세대를 증가시키고 변경 진행 상태와 현재 session ID를 기록한다. DB 변경이 완료되면 현재 세션의 `AUTH_GENERATION`을 새 세대로 저장하고 Principal 인덱스로 다른 세션을 찾아 `deleteById`로 정리한 뒤 변경 진행 상태를 제거한다.
- 관리자 비밀번호 초기화와 역할·주요 권한 변경은 하나의 Redis 원자 연산으로 세대를 증가시키고 유지 세션이 없는 변경 진행 상태를 기록한다. DB 변경과 물리 세션 정리가 끝난 뒤 변경 진행 상태를 제거한다.
- 로그인은 변경 진행 중 거부하므로 세대 증가와 DB 반영 사이에 이전 비밀번호나 권한으로 새 유효 세션이 생성되지 않는다.
- 세대 증가가 논리적 무효화의 기준이며 `findByPrincipalName`과 `deleteById`는 저장공간 및 인덱스 정리를 위한 멱등 후처리다.
- 세대 증가 후 DB 변경이 실패해도 이전 세대로 되돌리지 않는다. 기존 세션은 안전하게 무효화하고 변경 진행 상태를 복구 절차로 종료한다.
- 원자 연산이나 세대 조회가 실패하면 보안 이벤트를 성공으로 응답하지 않고 해당 인증 요청을 기본 거부한다. 물리 삭제 실패는 세대 차이와 변경 진행 상태로 차단된 상태에서 재시도하고 감사 로그를 남긴다.
- 세대 Key와 변경 진행 Key의 TTL은 어떤 사용자 세션 및 최대 복구 시간보다 길어야 하며 로그인과 보안 이벤트마다 갱신한다. 활성 세션이 있는데 세대 Key가 없거나 만료되지 않은 변경 진행 상태가 남아 있으면 복구 전까지 실패 폐쇄한다.

### 5. 권한은 사용자 직접 권한이 아니라 역할 기반으로 판단한다

#### 결정

기능 접근 여부는 사용자에게 직접 세부 권한을 부여하는 방식이 아니라 역할을 통해 판단한다. 역할은 여러 권한을 가질 수 있고, 사용자는 여러 역할을 가질 수 있다.

#### 근거

- `database.md`의 RBAC 도메인은 사용자에서 역할, 역할에서 세부 권한으로 이어지는 구조를 정의한다.
- `database.md`는 `user_roles`, `role_permissions`를 다대다 관계 해소를 위한 매핑 구조로 설명한다.
- `core-beliefs.md`는 기능 접근 여부를 역할 기반 권한 구조로 판단한다고 정의한다.

#### 영향

관리자 탭 접근이나 특정 기능 제어는 사용자 이름, 직급, 팀만으로 판단하지 않는다. 권한이 필요한 기능은 역할과 권한 구조를 기준으로 접근 가능 여부를 확인한다.

#### 역할·권한 카탈로그 계약

- 역할과 권한은 Migration으로 관리하는 고정 기준 데이터이며 런타임 동적 CRUD 대상으로 취급하지 않는다.
- 영속 식별에는 변경 가능한 표시 이름이 아니라 대문자 영문·숫자·밑줄로 구성된 안정적인 `roleCode`, `permissionCode`를 사용한다.
- 표시 이름은 관리자 화면과 문서 설명에 사용하는 별도 값이며, 역할명이나 권한명을 인가 판단 조건으로 사용하지 않는다.
- 사용자의 최종 권한은 사용자에게 연결된 모든 역할의 권한 합집합이다. 어떤 역할에도 매핑되지 않았거나 필요한 권한이 없으면 기본 거부한다.
- 현재 역할 적용 범위는 시스템 전체이며, 팀장처럼 특정 조직에만 적용되는 역할은 별도 Product Spec과 권한 모델이 마련되기 전까지 포함하지 않는다.
- 역할 상속과 `ADMIN` 전용 우회 규칙은 두지 않는다. `ADMIN`도 필요한 권한을 `role_permissions`에 모두 명시한다.

| 역할 코드 | 표시 이름 | 권한 코드 |
| --- | --- | --- |
| `ADMIN` | 총 관리자 | `SYSTEM_MONITOR`, `ACCOUNT_STATUS_READ`, `THEME_MANAGE`, `ROOM_RESOURCE_MANAGE`, `USER_MANAGE`, `TEAM_MANAGE`, `ROLE_MANAGE`, `PRIVILEGED_ACCOUNT_MANAGE` |
| `SYSTEM_ADMIN` | 시스템 관리자 | `SYSTEM_MONITOR`, `ACCOUNT_STATUS_READ`, `THEME_MANAGE`, `ROOM_RESOURCE_MANAGE` |
| `HR_ADMIN` | 인사 관리자 | `USER_MANAGE`, `TEAM_MANAGE` |

- `SYSTEM_ADMIN + HR_ADMIN`의 합집합에도 `ROLE_MANAGE`, `PRIVILEGED_ACCOUNT_MANAGE`가 없으므로 `ADMIN`과 같지 않다.
- 사용자 역할 조회·부여·회수는 `ROLE_MANAGE`를 요구하고, 관리자 역할 보유자의 정보·계정·재직·비밀번호 변경은 `USER_MANAGE + PRIVILEGED_ACCOUNT_MANAGE`를 모두 요구한다.
- 역할은 `ACTIVE + EMPLOYED` 사용자에게만 부여한다. 마지막 `ACTIVE + EMPLOYED + ADMIN` 사용자의 `ADMIN` 회수·비활성화·퇴직은 `409 LAST_ADMIN_REQUIRED`로 거부한다.
- 동일 역할 재부여와 미보유 역할 회수는 멱등 성공으로 처리한다.
- 역할 부여·회수의 시각, 행위자, 이전 상태는 DB와 보안 로그에 기록하지 않고 이력 조회 기능도 제공하지 않는다.
- 역할 또는 주요 권한이 변경되면 해당 사용자의 모든 세션을 무효화하고 다음 로그인에서 DB의 현재 권한을 다시 로딩한다.

### 6. 인증 방식은 자체 로그인만 제공한다

#### 결정

현재 서비스는 회사에서 발급한 계정과 비밀번호를 사용하는 자체 로그인 방식만 제공한다.

Google, Kakao, Microsoft 등 외부 인증 제공자를 이용한 소셜 로그인이나 기업 SSO는 현재 범위에서 제외한다.

#### 근거

- 현재 요구사항은 회사에서 관리하는 임직원 계정을 기준으로 로그인 기능을 정의한다.
- 사용자 계정과 인증 정보가 `users`, `user_credentials` 구조로 관리된다.
- 외부 인증 제공자 연동에 필요한 계정 연결, 정보 동기화, 장애 대응 정책이 별도로 정의되어 있지 않다.

#### 영향

- 로그인은 회사에서 발급한 계정 식별자와 비밀번호를 기준으로 처리한다.
- 외부 인증 제공자 계정과 내부 사용자 계정을 연결하는 기능은 구현하지 않는다.
- 추후 SSO 또는 외부 인증을 도입하려면 별도 Product Spec과 Design Doc을 작성한다.

### 7. 최초 로그인 시 비밀번호 변경을 강제한다

#### 결정

직원 계정 생성 시 시스템이 임시 비밀번호를 생성한다.

사용자가 초기 비밀번호로 최초 로그인에 성공하면 일반 서비스 화면으로 이동하지 않고 비밀번호 변경 화면으로 이동한다.

사용자는 새로운 비밀번호로 변경을 완료할 때 현재 세션을 유지하고 일반 서비스 화면으로 이동한다. 동일 사용자의 다른 세션은 모두 종료한다.

#### 최초 로그인 흐름

1. `USER_MANAGE` 권한이 있는 관리자가 직원 계정을 생성한다.
2. 시스템이 CSPRNG로 20자의 임시 비밀번호를 생성하고 대문자·소문자·숫자·특수문자를 각각 하나 이상 포함한다.
3. 사용자가 회사에서 부여받은 계정과 초기 비밀번호로 로그인한다.
4. 시스템이 최초 로그인 또는 비밀번호 변경 필요 상태인지 확인한다.
5. 비밀번호 변경이 필요한 사용자는 비밀번호 변경 화면으로 이동한다.
6. 사용자가 새로운 비밀번호를 입력하고 변경을 완료한다.
7. 비밀번호 변경 필요 상태를 해제한다.
8. 현재 세션을 제외한 동일 사용자의 다른 세션을 만료 처리한다.
9. 현재 세션으로 일반 서비스 화면에 접근한다.

#### 비밀번호 처리 기준

- 초기 비밀번호와 변경된 비밀번호는 평문으로 저장하지 않는다.
- 비밀번호는 BCrypt 단방향 해시 처리하여 저장한다.
- 평문 임시 비밀번호는 직원 생성·관리자 초기화·계정 재활성화 성공 응답에서 한 번만 반환하고 `Cache-Control: no-store`를 적용한다. 응답을 잃어버리면 복구하지 않고 다시 초기화한다.
- 비밀번호 변경 완료 전에는 일반 기능에 접근할 수 없다.
- 비밀번호 변경 성공 후 현재 세션은 유지하고 동일 사용자의 다른 세션은 더 이상 사용할 수 없도록 처리한다.
- 회사가 부여한 초기 비밀번호는 최초 로그인 이후 계속 사용할 수 없다.

#### 근거

- `requirements.md` NFR-002는 비밀번호를 암호화하여 저장해야 한다고 정의한다.
- 회사에서 생성한 초기 비밀번호를 계속 사용하면 계정 탈취 위험이 증가할 수 있다.
- 최초 로그인 시 본인만 아는 비밀번호로 변경하도록 하여 초기 인증 정보의 노출 위험을 줄인다.

#### 영향

- 사용자 인증 정보에는 비밀번호 변경 필요 여부를 판단할 수 있는 상태가 필요하다.
- 로그인 성공 이후에도 비밀번호 변경 여부에 따라 접근 가능한 화면이 제한된다.
- 비밀번호 변경 완료 시 현재 세션을 제외한 동일 사용자의 기존 세션을 무효화해야 한다.
- 비밀번호 변경 화면과 현재 세션 유지 흐름은 `auth.md` 및 `my-page.md`와 연결된다.

### 8. 관리자 역할은 총 관리자, 시스템 관리자와 인사 관리자로 구분한다

#### 결정

관리자 역할은 `ADMIN`, `SYSTEM_ADMIN`, `HR_ADMIN`으로 구분한다.

각 역할은 담당 업무에 필요한 최소 권한만 가진다. `ADMIN`은 최초 운영과 다른 관리자 계정 보호를 위해 모든 권한을 명시적으로 가지며 역할 계층으로 우회하지 않는다.

#### 총 관리자

총 관리자는 시스템 운영, 인사·팀 관리, 고정 역할 부여·회수와 관리자 역할 보유자 관리를 수행한다. 마지막 활성·재직 총 관리자를 제거하는 상태 변경은 허용하지 않는다.

#### 시스템 관리자

시스템 관리자는 확정된 v1 서비스 운영 조회와 제한된 공용 자원 설정을 담당한다.

주요 권한은 다음과 같다.

- 시스템 로그 조회
- 서비스 운영 상태 조회
- 장애 및 오류 현황 확인
- 사용자 계정의 활성 상태 조회
- 회사 대표 테마 관리
- 회의실 사진·장비 관리

시스템 관리자는 직원의 인사 정보, 소속 팀, 직급과 같은 인사 데이터를 임의로 수정하지 않는다.

#### 인사 관리자

인사 관리자는 직원과 조직 정보를 관리한다.

주요 권한은 다음과 같다.

- 직원 등록 및 조회
- 직원 기본 정보 수정
- 직원 계정 활성화 및 비활성화
- 직원 초기 비밀번호 발급 또는 재설정 요청
- 팀 생성 및 조회
- 팀 정보 수정
- 직원의 소속 팀 변경
- 직원의 직급 변경
- 조직도 정보 관리

인사 관리자는 시스템 로그, 서비스 상태, 회사 테마와 회의실 자원을 임의로 조회·변경하지 않는다.

#### 공통 권한 원칙

- 관리 기능은 역할에 연결된 권한을 기준으로 노출하고 실행한다.
- 프런트엔드에서 관리자 메뉴를 숨기는 것만으로 권한 검증을 대체하지 않는다.
- 백엔드는 모든 관리자 요청에서 역할과 세부 권한을 검증한다.
- 한 사용자가 여러 관리자 역할을 가질 수 있다.
- 역할을 여러 개 가진 사용자는 각 역할에 포함된 권한을 합산하여 사용할 수 있다.
- 개인정보와 시스템 운영 정보는 담당 역할에 필요한 범위에서만 조회할 수 있다.

#### 근거

- 시스템 운영과 인사 정보 관리는 책임과 접근 대상이 다르다.
- 하나의 관리자 역할에 모든 권한을 부여하면 불필요한 개인정보 접근과 시스템 변경 위험이 커진다.
- 최소 권한 원칙을 적용하여 역할별 책임과 권한 범위를 분리해야 한다.

#### 영향

- 관리자 화면은 시스템 관리 기능과 인사 관리 기능을 구분해야 한다.
- 관리자 API는 역할명만 확인하지 않고 필요한 세부 권한까지 검증해야 한다.
- `roles`, `permissions`, `role_permissions`, `user_roles`에 역할별 권한 구성이 반영되어야 한다.
- 관리자 역할 또는 권한 변경은 보안과 개인정보 처리 범위에 영향을 주므로 명시적인 검토가 필요하다.

## 미확정 사항

- 기기별 세션 관리 화면 제공 여부는 확정되어 있지 않다.
- 모든 기기에서 일괄 로그아웃하는 기능의 제공 여부는 확정되어 있지 않다.
- 비밀번호 길이, 문자 조합, 변경 주기 등 상세 보안 정책은 확정되어 있지 않다.
- 세션 유휴·절대 만료 시간, `SameSite`의 구체 값과 CSRF 방어 방식은 확정되어 있지 않다.
- 정의된 v1 범위를 넘는 시스템 운영 기능은 별도 Product Spec에서 확정한다.
